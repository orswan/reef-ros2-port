# P07 evidence: REEF-driven closed loop in Gazebo Harmonic (stand-in low-level loop)

Date 2026-10-01. Branch `p07-closed-loop` (from `main` `0f2aa63`). All runs
in the original container (the implementer has no Docker access).
Recordings in `recordings/p07_*` (ignored by Git; manifests inside).

**Scope and labels.** USER (2026-10-01): close the loop with the
simplified stand-in of [CONTROL_CHAIN.md §7](../CONTROL_CHAIN.md), drive
Gazebo's motor model directly, remove the stock controller, and record
initial stability and tracking. The stand-in (`reef_fc_standin`) is a
**development tool, not ROSflight**; it uses **truth** attitude and body
rates. REEF's inputs are **idealized** (truth attitude, idealized range,
simulated velocity observations, IMU vibration assumption). None of this is
ROSflight, hardware, or flight evidence.

## Chain (as run)

`/x3/imu` → IMU adapter → **REEF estimator** → `/x3/reef/xyz_estimate` →
**REEF controller** (`reef_control`, ported bit-exact in P06) →
`/x3/reef/command` → stand-in (firmware mux, attitude loop, allocation) →
`/x3/fc/motor_speed` → bridge → Gazebo `MulticopterMotorModel` ×4. World
`x3_closed_loop.sdf` has no `MulticopterVelocityControl`; nothing publishes
`/x3/cmd_vel` (the runner refuses to start otherwise). The controller's
inputs, read from the ROS graph in every run: `xyz_estimate` (estimator),
`desired_state` (scenario), `status` (stand-in), `/clock`; `is_flying` and
`pose_stamped` unconnected.

Reproducibility: every flight metric agrees across the three runs to within
0.07 s and 0.004 m; only the latency varies (host scheduling at real-time
factor 1). The latency criterion is **marginal on this host** (p99 12–24 ms
over four X3-gain runs plus run 1's 14 ms).

Observations:
- Yaw rate settles at 0.262 rad/s for a 0.3 command: the stand-in's yaw loop
  is P-only (no integrator), so rotor drag leaves a steady-state error.
- Before arming, reef_control publishes a throttle of about 0.34 (K5); the
  stand-in ignores it while disarmed. At REEF's takeoff detection the
  estimate jumps from the landed value (z_x0, 0.25 m) to the measured height,
  which shows as a throttle dip.
- The `dI` = 0 change removes the K2 windup symptom in this scenario; K2
  itself remains in the code and is asserted by `reef_check.sh control`.

## Amendment: end-of-run fly-away (2026-10-01, after the USER's GUI demo)

Observed by the USER in `reef_demo.sh closed-loop --gui`: the drone flew
off at the very end. Cause [V]: at the end of the scenario every ROS node
(estimator, controller, stand-in) stopped within about 1 s, while both
Gazebo processes ignored SIGINT for 5 s; the motor model keeps the last
commanded speeds, so the uncontrolled vehicle's thrust direction drifted
and it accelerated away. Verified in isolation: with the stand-in killed in
flight the vehicle kept accelerating on the frozen commands. The stock
world did not show it because its controller is a Gazebo system (it keeps
holding zero velocity until the server dies) and its scenario returns to
the start. No recorded metric was affected (scoring ends with the last
phase).

Fixes (criteria amended first, `38553a0`; implementation `85c1108`): the scenario returns (`back`, before the yaw phase), lands, and
disarms before it ends; the end state is judged; the stand-in commands zero
motor speeds on shutdown (re-verified: killed in flight, it stops the
motors and the vehicle falls and rests).

Run `p07_cl_land_a`: all judged checks PASS; end state disarmed, motors 0,
height 0.000 m, speed 0.000 m/s; returned to 0.030 m of the takeoff point
after `hover_back`, 0.018 m at the end; touchdown 1.07 s after `land`
started at 0.75 m/s (reported; the legacy altitude loop drives towards a
setpoint below the ground, so the touchdown is firm).
