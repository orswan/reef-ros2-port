# P02 evidence: estimator baseline and reference harness

Date 2026-09-30. Branch `p02-baseline` (from `main` `6736eeb`). All
commands ran in the original container, since the implementer has no Docker
access. Logs and outputs are in `build/baseline/` and `log/checks/` (ignored by
Git).

## Claim

Master `e4179f48` is selected as the fidelity baseline, and the simulation
revision `95987b51` is kept as a runnable comparison. The reference harness
executes the **unmodified** pinned sources, and an independent re-derivation
of the documented equations reproduces every step exactly. Legacy defects are
characterized, not corrected. The port tolerances are fixed and justified by a
measured floor.

## Key facts for a reviewer

| Question | Evidence |
|---|---|
| Are the compiled sources the originals? | `baseline/build_reference.sh` extracts them from the pinned Git objects and checks each SHA-256 against `baseline/provenance.json` (13 estimator files per variant plus 4 `reef_msgs` files). No patch is applied; the adaptations A1–A5 are listed in `baseline/README.md` |
| Is the reference checked by something other than itself? | `baseline/tools/independent.py` re-derives each step (XY EKF, Z KF with each variant's F/B/Q semantics, landing reset, partial/full updates, takeoff transitions, gates, RC switch) in numpy from the equations in BASELINE_DECISION §4, **not** from the C++. Result: 0 deviation over 266,796 steps and 41,200 gate decisions (tolerance 1e−12 relative) |
| Would the checks catch a wrong reference? | A deliberately mutated master build (bias coupling −dt → +dt) must fail both the independent check and the golden comparison (`negative` group in the report). During development the independent check also caught two harness bugs: `inf` parsed as 0, and an off-by-one in accelerometer initialization |
| Which differences between the revisions exist and who made them? | BASELINE_DECISION §2 and §5: merge base `ff29edc`; the simulation commit only disabled the χ² gates; everything else is master `e4179f4` (2021) |
| Why master? | BASELINE_DECISION §3: the per-step dt fix (the simulation revision doubles the vertical velocity at 250 Hz, `s09`), intact gating (the simulation revision goes NaN on a `-inf` range, `s10`), and it is pinned by the hardware bundle |
| What is wrong with master? | D1–D10 (§6). Most important is D1, stale re-fusion after a partial update (`s07`: the flag stays set for 999/999 steps and the velocity variance collapses to 7.4e−4) |
| Tolerances | §8: port vs reference 1e−9 × field scale, discrete exact. Measured floor 2.05e−12 (FMA, `-O3 -march=native`) and 0 (`-O0`); master vs sim ≥ 1.08e9× the tolerance |

## Uncertainties worth a reviewer's time

1. Whether D1 (flag clearing) is really accidental and should be corrected
   (C1). This affects every mocap/RGB-D fusion.
2. D2: the sign convention of the Z bias as used inside the XY filter, and
   whether the pre-2021 `+dt` coupling was the intended one.
3. The partial-update formula is checked against the code's structure and the
   cited paper's title, not a full reading of the paper.
