> ## 1. Is 1:1 parity with legacy master established?
>
> **Yes, for the controller (`reef_control` `12237b76`).**
> - [V] The reference harness compiles the pinned sources unmodified; their SHA-256 hashes match `provenance.json` and the git history.
> - [V] Parity compares the CSV output strings exactly: doubles at `%.17g`, float32 at `%.9g`, 142 columns, core and node.
> - [V] The source diff shows only plumbing changes. Math, statement order, float literals, clamping, the K4 `dt` test and the K6 NaN path are all unchanged. The core is built with `-ffp-contract=off` (no fused multiply-add).
> - [V] The estimator is untouched since R1 (`git diff 1ee999b bb47cf0 -- src/reef_estimator` is empty).
>
> Minor gaps:
> - `node_id` is not compared, although ACCEPTANCE says "every field".
> - `get_yaw` has no legacy helper vectors; it is covered only indirectly through parity.
> - Two startup-error rules are not listed as deviations in CONTROL_CHAIN §6 / INTERFACES §4.5:
>   - `max_roll`, `max_pitch` and `max_yaw_rate` must be finite and ≥ 0;
>   - integer values for `xIntegrator`/`uIntegrator` are rejected (roscpp ignored them silently).
> - [A] Durations beyond the int32 seconds range wrap silently instead of throwing. This cannot happen with real stamps.
>
> ## 2. Are the legacy quirks (K1–K13) and D1/C1 preserved honestly?
>
> **Yes.**
> - [V] K1–K9, K12 and K13 are asserted on the reference output and carry over to the port through exact parity. K1 was confirmed in this run: 739/739 steps match +kd.
> - [V] K10: the legacy code reads an uninitialized θ, which is undefined behaviour. Zeroing it in both the port and the harness is a documented choice, not a reproduction of legacy behaviour. The docs say so.
> - K11: "differentiators are never reset" is not asserted, only the integrator part.
> - [V] The X3 gain change (`dI` = 0) is in a config file with its reason; the K2 windup stays in the code.
> - [V] D1/C1 are unchanged since R1: C1 is on by default, and parity is checked with C1 off.
>
> ## 3. Do STATUS, ACCEPTANCE and INTERFACES match the findings?
>
> Mostly yes. The stand-in limits, the idealized inputs, the crash behaviours and the deferral of `Command.u[3]` to P10 are stated consistently. I found no claim of ROSflight, hardware or RGB-D evidence.
>
> Defects:
> 1. **The latency statement is inaccurate.** [V] `recordings/p07_cl_nominal_b` is a **headless** run, and it failed p99 ≤ 20 ms at 24 ms. The docs attribute 24 ms only to a GUI run on a loaded host:

>    - the STATUS line saying "one run failed" also counts wrong: two runs failed, one headless and one GUI.
>
>    The official check runs passed (12–20 ms), so the verdicts are valid. But the margin is thin, and one run sat exactly at the limit.
> 2. **Stale line.** INTERFACES §4 says "Not in the loop of any simulation yet (P07)." The controller has been in the loop since P07.
>
> Doc gaps:
> - **Firmware throttle rule missing.** The pinned firmware's `MIN_THROTTLE` (default true) uses the smaller of the RC and offboard throttle at all times. No doc mentions it; only a code comment does. The stand-in's RC fallback (throttle 0) and this rule are not modelled together. P10 must cover it.
> - INTERFACES §2 says "no staleness detection", but the stand-in applies a 100 ms timeout to `/x3/reef/command`.
> - STATUS header and the `main` contents line are stale (line 3 says "P07 merged", line 18 lists only P00–P05).
> - STATUS §7 has no human check for P07b (a dev-container run of `faults`).
> - The P07b skipped-check list omits `estimator`, `baseline` and `interfaces`, although the IMU adapter changed.
> - The `estimator_reset` recovery time varies between runs (4.6 s in P07b.md, 13.4 s in the official faults run); the spread is not reported.
> - ACCEPTANCE cites a true height of 0.987 m; the recordings show 0.983 m.
>
> The three corrected P07b characterizations (`384bec6`, made after the first runs):
> - **`velocity_loss`**: justified. Covariance can dip briefly with no measurements; the key property (no observations fused, σ grows 34×) is still asserted.
> - **`estimator_reset`**: justified by the recorded data.
> - **K10**: weaker. The evaluation moment moved from "6 s into the leg" to "first within 0.15 m" after a run had failed. The tolerance was not loosened, but the heading error at 6 s is no longer reported.
>
> No numeric threshold was loosened anywhere in the range.

> Evaluation weaknesses:

> - The "fault injected" check counts topic subscribers, and the bag recorder alone satisfies it. The downstream checks still catch a missed injection.

> ## 4. Is the closed loop end to end, and is truth confined?
>
> [V] The data path, from my trace and confirmed by the ROS graph in this run:
>
> IMU → adapter (truth attitude, declared) → estimator → `xyz_estimate` → controller → `Command` (mode 2; roll, pitch [rad], yaw rate [rad/s], F [0, 1]) → stand-in → `motor_speed` [rad/s] → bridge → 4 × `MulticopterMotorModel`
>
> - The controller's inputs are exactly: the estimate, the runner's setpoint, the stand-in's status, and `/clock`. `is_flying` and `pose_stamped` have no publishers in velocity mode.
> - The runner reads truth only for startup gating and the final record; its setpoints are open-loop phase tables.
> - The world has no `MulticopterVelocityControl` plugin and nothing publishes `/x3/cmd_vel`. Gazebo is the only physics owner.
> - Rotor geometry, motor order and spin directions in the config match the model. The FRD allocation signs are correct.
> - Test hooks live in the node layer only and are off by default.
>
> ## Verdict
>
> **Ready for simulation: yes, with conditions.** P08/P09 can proceed on this supported configuration:
> - Jazzy, Gazebo Harmonic, headless, idle host;
> - `x3_closed_loop.sdf`, `reef_control_x3_sim.yaml` (shipped quad gains with `dI` = 0);
> - the `reef_fc_standin` development tool;
> - idealized inputs (truth attitude, idealized range, velocity = truth + noise).
>
> The stand-in can make the outer loops look better than they will on real hardware. It uses truth attitude and noise-free rates, an 8 rad/s attitude loop with no integrators, linear thrust, exact allocation, and no RC, failsafe, MAVLink or PWM/ESC chain. The shipped quad gains also fail the first hover through K2 windup. Before closing, P10 must re-verify:
> - firmware `u[3]` semantics;
> - `MIN_THROTTLE` and RC override;
> - failsafe (throttle 0.3);
> - the nonlinear throttle-to-thrust map with the `wI` integrator;
> - the real latency budget;
> - the K4 first step with wall-clock stamps (`dt` ≈ 1.7e9 s);
> - gains on the real vehicle.
>
> **Physical flight: not authorized.** There is no ROSflight, hardware or flight evidence. The legacy system has no protection against estimate loss, controller restart or low-level death, and the dry-run sink refuses `hardware:=true` until P10. An R3 hardware review is required.
>
> Before merging P07b, I'd fix the latency wording, the stale INTERFACES and STATUS lines, the missing `MIN_THROTTLE` note, and the always-pass items. I can save this review as `docs/reviews/R2.md` and make those doc fixes if you want; I haven't changed anything yet.
